## What was built this session

### `app/grocy_client.py`
Async HTTP client for Grocy. Auth via `GROCY-API-KEY` header. `GROCY_URL` env var must NOT include a trailing `/api` — the client appends that itself (normalised via `.removesuffix("/api")` in `__init__`). SSL verification is disabled (`verify=False`) because Grocy runs behind Tailscale Serve, whose certs are not trusted by Python's certifi bundle.

Three private fetch methods (`_fetch_product_groups`, `_fetch_products`, `_fetch_stock`, `_fetch_locations`) and three public methods (`get_product_groups`, `get_products`, `get_stock`). Stock entries from `/api/objects/stock` are individual purchase batches — `aggregate_stock()` sums them by `product_id` and resolves `location_name` via a `/api/objects/locations` fetch. `stock_unit_name` is not yet resolved (requires `/api/objects/quantity_units` + product cross-reference).

Confirmed API shapes documented in `plans/grocy-api-shapes.md`.

### `app/controllers/beverages.py`
Cache check → Grocy refresh → DB read → `BeveragesResponse`.

- `get_beverages(host_mode)` — checks `CacheStatus.is_grocy_stale()`, calls `_refresh()` if stale, then `_build_response()`
- `_refresh()` — calls `GrocyClient`, upserts groups/products, replaces stock, marks cache refreshed
- `_build_response()` — reads DB, filters `amount > 0`, nests children under parents, strips variant prefix from child names (`"High Noon | Pineapple"` → `"Pineapple"` when nested under parent), sorts products and groups alphabetically
- `serving_notes` (from `GrocyProduct.description`) stripped in guest mode
- Groups returned as-is from Grocy — no display-group remapping in the backend

**Bug fixed this session:** `GrocyProduct.upsert_all` in `db.py` now sorts products so parents are inserted before children, preventing a self-referential FK violation when the API returns children before their parent.

### `app/controllers/crafted_drinks.py`
Cache check → Notion refresh → DB read → availability computation → `CraftedDrinksResponse`.

- `get_crafted_drinks(host_mode, tags)` — checks `CacheStatus.is_recipe_stale()`, calls `refresh()` if stale
- `refresh()` — fetches all drink pages, then concurrently fetches page blocks + ingredient rows per drink using `asyncio.gather` with a `Semaphore(3)` to respect Notion's 3 req/s limit. Writes to DB via `CraftedDrink.replace_all()`
- `_build_response()` — reads from DB, resolves each ingredient against `IngredientMapping`, checks `GrocyStockEntry` for stock, computes `available` (True if all **matched** ingredients are in stock — unmatched do not affect availability), filters by tag intersection if `tags` provided
- `host_notes`, `author`, `unmatched_ingredients` stripped in guest mode

**Bug fixed this session:** `content.method` (from `get_page_blocks`) was not being written into the data dict before `replace_all`. Added `data["method"] = content.method`.

## False assumption — ingredient mapping

The `IngredientMapping` table and `GET/POST/DELETE /api/mappings` endpoints were built with the assumption that mappings between Notion ingredient names and Grocy products are **created entirely by hand** via the API. This was wrong.

The original plan called for **relation building** — some form of automatic or assisted matching between Notion ingredient names and Grocy product names. The manual-only mapping approach was an incorrect inference made this session and should be revisited.

The current DB schema and endpoints are not necessarily wrong, but the **mapping creation flow** needs to be redesigned. Possible directions:
- Auto-match on exact name (case-insensitive)
- Fuzzy match with a confidence threshold, surfacing suggestions in the host UI
- Host UI presents unmatched ingredient names alongside a searchable Grocy product list — host confirms or corrects the suggestion

What was built assumes the host calls raw API endpoints to create mappings. That assumption should be discarded.
